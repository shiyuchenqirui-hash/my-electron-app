## 1. 目标与适用边界

本次学习的背景是：已有前端经验，正在补齐 PC 客户端的运行模型、平台能力、调试和分发知识。目标不是把 Electron 官网全部读完，而是能够在遇到问题时判断代码在哪运行、谁负责处理、状态什么时候变化，以及怎样验证。

**用户反馈**：当前项目和学习颗粒度适合接触新方向。**「推断」**：它适合的原因是，每个实验的业务足够简单，注意力可以集中在平台机制上，同时又包含真正的菜单、窗口、IPC 和打包行为，而不是只背概念。

本文的依据分为三类：当前仓库代码、已有学习路线、当前会话中的问题与操作反馈。会话中出现过的日志或截图只支持对应场景，不视为所有平台、版本、窗口组合都已验证。

本文是一次性复盘，不修改业务代码、不重新安排整条学习路线，也不表示 App 技术栈已经选定。已有进度继续由 [Electron 学习路线与进度记录](impl_electron_learning_roadmap.md) 管理。

## 2. 项目大小与学习颗粒度

### 2.1 一个持续演进的小项目

本项目没有从复杂客户端开始，而是保留了三组直接可操作的内容：

- Menu Counter：菜单加减数字，观察 Main、Preload、Renderer 的消息往返。
- Settings：打开和关闭模态窗口，观察窗口关系、对象身份与生命周期。
- 导航实验：修改 hash、切换本地页面、请求新窗口、打开或拒绝外链。

这些功能共享同一个项目环境，不必每学习一个 API 都重新处理依赖、入口、启动和调试配置。Electron Fiddle 可以用于快速隔离某个 API；需要跨章节反复观察的机制，再放回这个持续演进的项目。

**「推断」**：若同时引入登录、复杂状态管理、后端接口和组件体系，出现问题时就更难区分平台机制与业务实现。因此，学习 Demo 应围绕真实平台 API 展开，但暂不追求产品完整度。

### 2.2 一轮一个机制，而非一轮一个大章节

一次学习可以围绕“点击 Close 后，究竟是谁关闭窗口”展开，不需要同时完成所有窗口 API。颗粒度以能够亲自操作、看清变化并复述为准，不用页数或代码量衡量。

一轮至少包含：一个具体问题、一个入口、一个可观察结果、一个解释。需要对照时，只改变一个关键条件，例如正常 HTML 与不存在的 HTML、同页 hash 与跨文档链接。

本次会话已经多次采用“先提出几个阅读问题，用户回答，再逐一解释和实验”的节奏。回答“不知道”是定位下一步的有效信息，不必继续堆叠更多资料。

### 2.3 先主干，后能力分支

不按官网左侧目录从上到下阅读。先建立运行模型、通信、生命周期、安全边界与调试入口；设备访问、应用内购买、原生模块等按具体需求补充。

API Reference 用来查询当前问题，不当作必须背完的课程。工具选择也保持单主线：本项目已有 Playwright Test，不为了“都学过”再同时引入另一套测试框架。

## 3. 每一轮学习的固定闭环

### 3.1 先给官方入口，再提出问题

用户在会话中明确要求：后续学习先给官网链接，再给逐个环节的解释，最后落到项目文件。解释不能取代原始资料。

阅读前固定关注以下问题，可按主题删减：

1. 代码运行在哪个进程、线程或上下文？
2. 对象由谁创建、谁持有，权限由谁控制？
3. 这是发起请求、准备就绪，还是已经完成？
4. 失败、重载、关闭或重新启动时，哪些状态留下、哪些消失？

例如读 `loadFile()` 时先区分发起加载和加载结果；读 IPC 时先区分页面到 Preload 的上下文调用，以及 Preload 到 Main 的进程间通信。

### 3.2 先预测，再观察，最后解释

下面是本次方法的归纳，不要求每轮都新增文档或自动化测试。

```mermaid
flowchart LR
    Question["一个具体问题"] --> Source["官方资料与项目入口"]
    Source --> Predict["先说预期与不确定点"]
    Predict --> Experiment["最小操作或对照实验"]
    Experiment --> Evidence["日志、断点、页面或对象状态"]
    Evidence --> Explain["解释并修正理解"]
    Explain --> Record["记录结果与下一步"]
```

这条闭环的重点是允许实测推翻预期。发现反例时应修正结论，不把异常日志硬解释成符合原先说法。

### 3.3 代码以调用链为组织单位

讲解时给出“触发入口、经过的函数、跨越的边界、产生的结果”，再让用户逐个打开文件。优先保留便于断点定位的具名函数，而不是把关键逻辑都压成一行。

每个断点要有明确问题：到这里时参数是什么、上一层是谁、下一句会修改什么。不是为了遍历所有框架内部代码而一直单步进入。

### 3.4 完成标准是能够预测变化

一轮的自检标准是：能自己触发操作，能找到处理位置，能说明参数和状态变化，并能回答“改掉这个关键条件，行为为什么不同”。暂时做不到时，记录具体卡点，而不是标记“全部掌握”。

可选的巩固动作是：不看讲解复述调用链，或独立修改一个参数并预测结果。此项是后续建议，不表示本次每轮都已完成这种复测。

## 4. 当前项目的具体样本

### 4.1 计数器：用极小业务观察完整通信

官方对应资料是 [Electron IPC 教程](https://www.electronjs.org/zh/docs/latest/tutorial/ipc)。当前代码入口如下：

| 环节 | 文件与定位符号 | 要回答的问题 |
|------|----------------|----------------|
| 菜单触发 | [main.js](../../main.js) 的 `createWindow()`、`sendCounterUpdate()` | Main 为什么通过指定窗口的 `webContents.send()` 发消息？ |
| 接收和过滤 | [preload.js](../../preload.js) 的 `onUpdateCounter()` | 为什么只传 `value`，不把原始 IPC event 传给页面？ |
| 页面更新 | [renderer.js](../../renderer.js) 的 `handleUpdateCounter()` | `value`、`oldValue`、`newValue` 分别是多少？ |
| 页面回传 | `window.electronAPI.counterValue()`、Preload 的 `sendCounterValue()` | 哪一步只是调用桥接函数，哪一步是真正发 IPC？ |
| Main 接收 | `handleCounterValue()`、`ipcMain.on('counter-value', ...)` | DOM 更新和 Main 收到消息是不是同一个执行位置？ |

数字加一不是学习目标；它是观察参数和控制流的载体。完整往返把抽象的“多进程通信”转换成可以在多个文件中停住、检查的代码。

### 4.2 Settings：用关闭按钮连接平台生命周期

在 [main.js](../../main.js) 中，`createSettingsWindow()` 使用 `parent`、`modal`、`show: false` 创建窗口，通过 `ready-to-show` 显示；`close` 和 `closed` 分别记录关闭前后。

实际关闭入口在 [settings-renderer.js](../../settings-renderer.js)：按钮点击调用 Preload 暴露的 `closeSettings()`，发出 `settings:close`。Main 的 `handleCloseSettings()` 根据 `event.sender` 找窗口，只允许当前 Settings 窗口执行关闭。

这个实验需要分别确认：父子关系、模态交互、独立 `webContents`、sender 身份、关闭事件，以及窗口对象是否销毁。不同的 `webContents.id` 不能直接证明不同的操作系统进程 PID。

会话中用户曾指出模态窗口没有方便的关闭能力。复盘要点是：实验必须提供完整、可重复的操作入口和退出方式，否则调试平台机制时会被 Demo 本身卡住。

### 4.3 加载失败：用反例修正事件理解

官方对应资料是 [webContents API](https://www.electronjs.org/zh/docs/latest/api/web-contents)。会话中一次重新启动后的日志包含下面这段顺序：

```text
[settings] did-start-loading
[settings] did-fail-load { errorCode: -6, errorDescription: 'ERR_FILE_NOT_FOUND', ... }
[settings] dom-ready
[settings] did-finish-load
[settings] failed to load Error: ERR_FILE_NOT_FOUND ...
[settings] closed
```

直接证据是：该次目标文件加载失败后，仍然观察到了 `dom-ready` 和 `did-finish-load`，同时 `loadFile()` 的 Promise 进入失败处理。因此不能仅凭 `did-finish-load` 宣布目标文件加载成功。

“后续事件来自 Chromium 错误文档”是当时的**「推断」**，不能作为已验证根因。`closed` 则需要结合失败处理中的销毁代码解释，不能认为加载失败天然等于窗口关闭。

方法上，先定位本次启动的日志边界，再重新运行最小反例。保留实际事件顺序，不用预设的教科书顺序覆盖日志；也不把 `ready-to-show`、DOM 就绪、加载结束混为一个时刻。

### 4.4 导航：相似操作要分开比较

[settings.html](../../settings.html) 与 [navigation-target.html](../../navigation-target.html) 提供了 hash、跨文档、`target="_blank"`、官方外链和拒绝目标。`main.js` 中的 `getSettingsNavigationAction()`、`handleSettingsNavigation()`、`setWindowOpenHandler()` 对应不同处理入口。

本次会话的观察包括：hash 导航出现 `isSameDocument: true` 和 `did-navigate-in-page`；普通链接导航出现可取消导航事件及后续加载事件；被拒绝的新窗口请求记录 `window-open-request`。

学习要点不是记住每个事件名称，而是区分：同一文档的位置变化、当前窗口切换文档、新窗口请求和系统浏览器打开外链。跨文档会重建页面上下文，但不能仅据此断言 Renderer 的操作系统进程也一定更换。

### 4.5 Smoke Test：把少量里程碑保存为可重复检查

[tests/electron.smoke.spec.js](../../tests/electron.smoke.spec.js) 当前有两个测试：应用启动与桥接 API 存在；模态 Settings 的窗口关系与关闭。入口是 `_electron.launch()` 启动项目 `main.js`。

测试通过 `Page` 操作页面，通过 `electronApp.evaluate()` 检查 Main。它测试真实的开发态 Electron，不是普通 Chromium 页面，也不是 Forge 打包后的 ZIP 或 `.app`。[Playwright Electron 官方文档](https://playwright.dev/docs/api/class-electron) 将该支持标记为 experimental。

当前源码没有把所有手动 IPC、导航、崩溃实验都纳入测试。学习阶段先保留少量稳定检查，不以全覆盖率作为继续学习的前提；本文只核对测试代码，没有重新运行测试。

## 5. 调试与证据校验

### 5.1 先选执行目标，再找断点

[.vscode/launch.json](../../.vscode/launch.json) 已区分 `Main`、`Renderer - Main Window` 和 `Renderer - Settings Window`。两个 Renderer 配置通过页面 URL 筛选目标，不是“连接某个端口就自动调试全部窗口”。

本次曾遇到 Preload 找不到、断点空心、窗口尚未创建就附加 Renderer 等问题。方法是先确认运行入口、目标页面、加载的脚本与附加会话，再判断业务代码；不能看到断点未命中就认定代码没有执行。

Main 可从 VS Code 或 Node Inspector 调试，页面和 Preload 可从对应 Renderer 调试目标观察。VS Code 和窗口 DevTools 可能同时显示同一目标暂停：它们是调试前端，不是两份独立运行的业务代码。

### 5.2 实验开始前减少历史干扰

- 清理或禁用与本轮无关的旧断点，确认应用没有停在上一轮的位置。
- 确认当前只有需要的应用实例和调试会话，不凭窗口标题判断是否同一实例。
- 清空输出，或标记本次启动边界；有必要时对照 PID、窗口 ID、`webContents.id`。
- 启动后再附加对应页面，执行一个动作，收集这一轮的日志。
- 临时 `debugger` 或控制台监听用完后清理，不把临时措施误写成正式能力。

需要早期暂停时，可以使用临时 `debugger`；它是帮助定位的手段，不是学习终点。调试器自身造成的暂停，也不能当作应用自然无响应的证据。

### 5.3 区分三种证据

| 类别 | 可以说明什么 | 不能替代什么 |
|------|--------------|--------------|
| 官方资料 | API 契约、支持边界、平台注意事项 | 当前项目是否按该方式实现 |
| 当前代码 | 实际入口、判断条件、配置与函数调用 | 实际运行是否成功、精确事件顺序 |
| 运行日志、断点、截图 | 本次版本和操作下观察到了什么 | 所有平台、所有组合的普遍结论 |

来自逻辑分析的结论标为「推断」，尚未执行的操作标为“待实测”。例如依赖已安装、发布资产已出现，并不能自动证明真实自动更新已完成。

### 6.2 本次复盘时的学习位置

已有代码和会话覆盖了 IPC 往返、窗口创建与关闭、多窗口断点、页面加载和导航安全。学习路线中 `webContents` 与导航部分仍有较早的“待读”标记；本文记录的是本次会话进展，不声称旧进度表已同步更新。

## 7. 迁移到 App 的方式

### 7.1 迁移问题框架，不机械迁移 Electron 名词

以下是**「推断／建议，尚未实践」**。未来先明确目标是原生 Android、iOS、React Native、Flutter 或其他路线，再选对应官方入门资料与调试方式。不能先假设每种 App 都有 Main、Preload、Renderer 的一一对应结构。

| 本次 Electron 学习的问题 | 未来 App 中对应的学习问题 |
|---------------------------|---------------------------|
| 代码在哪个进程、上下文运行？ | UI、后台任务、平台代码如何运行，实际线程模型是什么？ |
| 窗口关闭、页面重载后谁还活着？ | 页面退出、后台切换、进程终止后，哪些对象和状态还存在？ |
| 页面怎样受控调用原生能力？ | 当前技术栈如何调用平台 API，谁负责权限与参数校验？ |
| 导航、新窗口和外链分别由谁处理？ | 应用内路由、系统链接、深链如何进入应用并校验？ |
| 开发态测试证明了什么？ | 模拟器、真机、调试包、发布包各验证了哪一层？ |

相同的是提问和实验方法，不是底层实现。某个框架的桥接机制也不能未经核实就套用为“Electron IPC 的手机版”。

### 7.2 用一个小 App 延续同样颗粒度

建议从一个计数页与设置页起步，一轮只增加一个平台问题：页面切换与状态、生命周期、一个权限受控的本地能力、深链，随后再补调试包与发布包的差异。

每轮仍先给官方链接，定位实际文件，预测结果，再亲自操作。涉及权限弹窗、系统行为或设备差异时，记录设备与系统版本；模拟环境的结果不能自动替代真机结论。

等运行模型和生命周期清楚后，再接复杂业务或阅读大型工程。业务工程用于确认“实际项目为何这样做”，小实验用于排除业务复杂度；两者是互补证据。

## 8. 与 AI 协作的可复用约定

本次协作中有效的约定是：AI 提供官方资料入口、文件定位、解释与最小实验，用户亲自操作、提出不理解处、返回结果。工具或 AI 的成功报告不能代替用户操作反馈，也不能补全未观察到的状态。

后续可以直接使用以下提示词：

> 我在学习一个新平台，请参照这次 Electron 小项目的颗粒度陪我推进。先根据当前进度选一个主题并给官方链接，再给少量带问题的阅读提示。讲解要结合当前文件、函数和真实调用链；需要实践时，只增加验证本轮机制的最小代码，提供完整的触发与退出方式。操作步骤按界面点击位置说明，不只给功能键。让我先预测并亲自试用，再根据日志或截图校正理解。不要按官网目录线性讲完，不扩成业务系统；区分已阅读、已实践、推断与待验证，不提前进入下一大主题。

对于“帮我解释”与“帮我修改代码”要分开执行。需要代码变更时先说明范围；提交和推送按明确指令处理。当天停止学习时，留下一个可运行的检查点和单一下一步，而不是一长串新任务。

以后复用这套方法时，先问自己：本轮是否足够小，是否真的能操作，是否知道要观察什么，是否留下了可追溯的结论。方法的价值在于让理解可以被验证，而不是增加文档或工具数量。
